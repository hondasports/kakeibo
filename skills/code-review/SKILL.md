# コードレビュー

## 深度判定

レビュー直前に `git diff <base>...HEAD` と未コミット・未追跡の内容、共有callerを確認する。実差分を4軸（blast_radius / data_security / reversibility / uncertainty）と強制条件（floor_triggers）で評価し、根拠をtier_rationaleへ記録して `node scripts/review-depth.mjs` へ渡す。語彙は `--vocabulary` で確認できる。返された最低深度（T1/T2/T3）以上の確認を実施する。深める必要があればapplied_tierを指定し直す。

## 反復プロトコル

レビューと修正はラウンドで管理する。

1. 算出ティアの確認項目でレビューし、指摘を finding としてid・状態・根拠つきで列挙する。
2. 各findingを修正するか、反証で不成立とするか、合意済みスコープとの照合根拠で対象外とする。修正は再現条件での再検証・再レビューが終わるまでopenのままとし、閉じる根拠に修正commit・差分と確認結果を残す（パッチ済みでも再現テスト失敗ならopen、前提不成立の証拠があれば棄却）。有効だが後回しの指摘は棄却と分け、受入条件を満たせない先送りは収束に数えない。
3. 変更があれば影響範囲を限定して再レビューする。対象は変更hunk・修正が影響する項目・前回のopen findingsだけで、全差分を毎回見直さない。共有caller・入出力契約・受入条件・環境の前提が変わった場合や、影響を特定できない場合は、関連するclosed findingsを再評価し、必要ならimpact-analysisと深度再判定へ戻る。範囲を広げた理由と対象を記録する。
4. open findingが0件（全件に根拠あり）で収束。進展（未解決の減少・新しい検証結果・原因仮説の更新）がある間は、ユーザー指定の制約と実行予算内で継続し、3ラウンドごとに方針を再評価する。継続・方針変更・外部入力待ち・予算到達を区別し、上限到達は未完了として報告する。新しい証拠なしに同じfindingが再発する場合は `skills/incident` へ切り替える。

内容・要求・環境が変わったら検証・評価・レビューを取り直す。

## Checker

セルフレビューは自己評価であり独立レビューではない。必須条件（review-depthが返すセルフレビュー項目、repository policy・ユーザー指定で必要なCIと承認）と、利用可能な補助観点（Devin Review等のボット指摘）を分ける。観測可能な結果は固定の順番待ちにせず確認する。ボット未導入・承認不要なら他の必須条件だけで完了でき、承認必須ならCI成功でも待機する。T3相当（認証・schema・データ削除等）でも必須セルフレビュー項目は実施し、独立観点が必要な部分は未確認リスクと証跡を具体化してボット・人間レビューへ引き渡す。委譲を確認省略や完了扱いの根拠にしない。

## リモートの指摘

PR上のボット・人間の指摘も同じ型で扱う。`node scripts/collect-pr-findings.mjs --pr <番号>` でinlineスレッド・レビュー本文・PR会話コメントを機械収集し（収集範囲は出力の `scope` に明記）、各件を修正 or 棄却（根拠）で閉じる。「指摘なし」は3種すべての収集結果が0件の場合に限る。詳細は `skills/pr-aftercare`。

レビュー結果として、元要求、差分の要求対応、検証の妥当性、manual確認結果、残findingをPR・作業報告へ記録する。
