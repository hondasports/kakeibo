# ssot の観点

同じルール・値・処理が複数箇所で定義されていて、食い違っている、または食い違っても気付けない構造になっている箇所を探す。#1044 がこのテーマの例。

## 探すもの

- **同じ値の手書き。** 列挙値（status・種別など）、上限値、定数が、ドメイン・Convex の validator・schema・フロントの型に別々に書かれていないか。正本の型は、ドメインの `as const` 配列から作る形になっているか。
- **同じ判定・計算の二重実装。** 日付の計算、金額の整形、検証ルール、表示名の解決などが、ドメインと画面などで別々に実装されていないか。入力を変えて両方を動かし、結果が食い違うかを確かめる。
- **互換用の入口。** re-export だけのファイル（shim）や「新規コードは正本を直接使う」と書かれた入口が、使われ続けていないか。
- **使われていない旧実装。** `src/main.tsx` からたどり着かない画面やコードが残っていないか（静的な import・re-export・文字列の dynamic import をたどる）。残っていると、現行と違うロジックが再利用されたり、修正だけが入り続けたりする。
- **期限付きのコード。** 「1リリース残す」などの一時的な互換コードや、一回限りの migration が、期限を過ぎても残っていないか。消す条件が記録されているか。

## 出すときの注意

- たまたま同じ値で、意味が独立しているもの（例: 2つのグラフの表示件数）は、統合しないものとして「対象外と理由」に書く。
- 境界ごとに意図して違う契約（例: 2値と3値の環境モデル）は、統合しない。
- 削除の候補は、ファイルごとに参照を確かめる。shim の向こうにあるテストが正本の関数を検証していることがある（テストを消すと正本のテストが減る）。
- 値の集合や挙動が変わる統合は「挙動を変える」と印を付ける（親PRに積まず個別PR）。
