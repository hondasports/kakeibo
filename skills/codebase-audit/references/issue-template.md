# 点検結果の Issue の形

タイトル: `[audit:<テーマ>] <範囲>の点検（YYYY-MM-DD）`。例: `[audit:tests] lib/domain/receipt/tax の点検（2026-11-01）`

同じテーマの Issue が開いている場合は、新しく立てずに、下の「今回の結果」以降をコメントとして追記する。

```markdown
## やりたいこと（Human Request）

> （依頼の文をそのまま引用する）

---

以下は Agent が調査して補完した内容。行番号は `<branch>` の `<commit>` 時点のもの。

## 範囲と観点

- テーマ: `<テーマ>`（`skills/codebase-audit/references/<テーマ>.md`）
- 範囲: （例: `convex/**`）
- 前回の点検: #<番号>（無ければ「なし」）

## 状態の凡例

- **再現済み**: 実際に動かして確かめた
- **確認済み**: コードを読んで確かめた（動かしてはいない）
- **要判断**: 直し方に仕様の判断が要る

## 今回の結果

| # | 優先 | 項目 | 状態 | 前回との関係 |
|---|---|---|---|---|
| 1 | P1 | （短い名前） | 再現済み | 新規 / 継続 / — |

### 1. （項目名）（P1）

**内容**
- 何がどこにあるか（`path:line`）

**状態: 再現済み**
- 確かめた方法と結果（実行したコマンド・入力・出力）

**直し方**
- 正本をどこにするか、何をどう変えるか
- 挙動を変えるか / 認可・グループ境界・データ削除に触るか（触るなら「個別PR・独立レビュー」）

## 直ったもの（前回からの差）

- （前回の項目番号と、直したPR）

## 対象外と理由

- （統合しない・直さないと決めたものと、その理由。根拠の Issue・PR）

## 次回に回すもの

- （件数の上限を超えた、優先度の低いもの）

## 進め方の案

1. 挙動を変えない変更（親PRに積めるもの）: 項目 …
2. 挙動を変える変更（個別PR）: 項目 …
3. 認可・グループ境界・データ削除に触る変更（個別PR・独立レビュー）: 項目 …
4. 仕様の判断が要るもの: 項目 …

## 未確認

- （推測にとどまったもの。何を確かめれば確定するか）
```
