# tests の観点

ユニットテストと E2E を見直す。目的は件数を増やすことではなく、**テストがプロダクトの守っている性質の一覧として読め、壊したら落ちる**状態にすること。テストの書き方の確認点は `skills/repo-code-review/references/unit-test.md`・`references/e2e.md`、E2E の作り方は `skills/e2e-spec-authoring` が正本。

範囲が広いので、1回では A・B・C のどれか1つ、または税ドメイン・認可・日付のような重要な範囲に絞る。

## A. 守れていないテスト（壊しても落ちない）

- **修正を外したら落ちるか。** 重要な不変条件（税の計算、認可、JST の日付境界）について、本体の判定を一時的に外して、テストが落ちるかを確かめる。落ちなければ、そのテストは守れていない。外した変更は必ず元に戻し、`git status` で確かめる。
- **消したコードにしかなかった保証。** 削除・リファクタの履歴を見て、消したコードのテストが守っていた性質が、今のコードとテストにも残っているかを確かめる（例: 旧UIにしかなかった「未検証の内訳を確定扱いしない」）。
- **環境で結果が変わる。** `TZ` を変える、負荷をかけるなどで、結果やタイムアウトが変わるテストがないか。

## B. 見えていないテスト（あるのに気付けない・選ばれない）

- **同じ関数のテストが分かれていないか。** shim や re-export を通して正本の関数を検証しているテストがないか。import をたどって、正本のテストと重なり・漏れがないかを見る。
- **E2E の選び方の漏れ。** push 前のゲートは `e2e/spec-map.json` の対応で spec を選ぶ（`scripts/select-e2e-specs.mjs`）。変更したパスに対して、影響を受ける spec が選ばれない組み合わせがないか。`spec-map.json` のキーにあるのに対応する spec が足りないパスや、削除されたファイル（差分の判定から外れる）を確かめる。実際に選ばれた spec は、ゲートの E2E のログ（`$TMPDIR/suzumemo-prepush-*/e2e.log`）で確かめる。`verify:prepush` の画面出力には spec の名前が出ない。
- **文書を検査するテスト。** `tests/workflow/*.test.ts` のように `readFileSync` で文書を読むテストは、`vitest related` では選ばれない。何を検査しているかと、検査先が正本になっているかを見る。
- **不安定なテスト。** CI の flaky の集計（`scripts/report-flaky-e2e.mjs` の出力、GitHub Step Summary）や、リトライで通ったテストを見て、繰り返し不安定なものを挙げる。

## C. 仕様として読めないテスト

- **事故の状況だけを確かめているテスト。** Issue 番号を名前に持つテスト（例: `updateForReviewTax.issue890.test.ts`）や、特定の入力だけを確かめるテストが、どの性質を守っているかがテスト名（What）から読めるか。同じ性質を守るテストがまとめられないか。
- **拒否・失敗の経路。** 正常系だけでなく、未認証・別グループ・権限なし・入力不正・部分失敗のテストがあるか。システム管理者の操作は `convex/systemAdminSecurityMatrix.test.ts` に表で揃っている。家計データのグループ境界にも同じように揃っているか。
- **E2E と unit の役割分担。** E2E でしか確かめられないこと（認証、画面の状態の移り変わり、実DB）に絞れているか。unit で足りる確認を E2E で重ねていないか（push 前のゲートの E2E は1回14〜15分かかる）。
- **受入条件との対応。** Issue の受入条件から、それを確かめるテストまでたどれるか（`skills/implementation` の対応表の形）。

## 出すときの注意

- 「意味のないテスト」と判断するときは、そのテストを消すと何が守られなくなるかを書く。主観だけで削除を提案しない。
- 足りないテストを指摘するときは、守りたい性質（What）と、どの層（unit / convex-test / E2E）で確かめるのがよいかを書く。
- テストの追加・削除は挙動を変えないので親PRに積めることが多い。ただし、足りないテストを書いたら本体の不具合が見つかった場合は、その修正を個別PRにする。
