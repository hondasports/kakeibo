# 実装

## 適用

アプリの振る舞いを変えるコード変更。pure docs・READMEだけの変更は対象外（`AGENTS.md` の例外に準ずる）。

preflightの後、**最初の編集の前**に読む。コミット前にもう一度使う。exportされた関数・型の意味を変える、複数ディレクトリにまたがる、認可・永続データ・外部writeに触れる、または変更対象の識別子が分からない場合は、先に `skills/impact-analysis` で調べ、その結果を下の対応表に入れる。

## 編集前: 何を証明するかを決める

受入条件ごとに「確認方法」を決め、対応表を作る（前向き）。確認方法を決める前に、テストやコマンドを選ばない。

```text
| 受入条件 | 確認方法 | 期待結果 |
```

実装の種類で、先にやることが違う。

| 種類 | 先にやること | 確認すること |
| --- | --- | --- |
| バグ修正 | 修正前に失敗する再現テストを書く | 修正前に失敗し、修正後に成功する |
| 機能追加 | 受入条件を表すテストを書く | 実装前に失敗し、実装後に成功する |
| リファクタ | 振る舞いを固定する既存テストが足りるか確かめる | 前後で成功のまま。新規テストは原則増やさない |
| UIのみの変更 | unit・E2E・目視のどれで確かめるか決める | 決めた方法で確認する |

## 原因が確定していないとき

- まずローカルの証跡（ログ・既存fixture・テストデータ）で再現を試みる。足りないときだけ、本番の実データ・実画像に頼る。再構成した入力だけで原因を断定しない。
- 本番データへのアクセスや持ち出しは、対象と操作の明示承認を得てからにする（`AGENTS.md` の本番・不可逆操作の契約）。承認前は、承認済みの匿名化サンプルをユーザーへ依頼する。
- 「再現できた条件」と「推定」を分けて記録する。推定だけで、税や認可などのガードを緩めない。
- 実データ由来の再現テストは、個人情報・識別子を除き、数値と構造だけにする。

## 実装中: 対応表を更新する

次のどれかが起きたら、その場で表に行を足す。

- 新しい振る舞いを変えた
- 見つけた不具合を直した
- 計画に無かった修正を足した

## red→green の確認方法

1. 再現テストを書き、修正前に失敗することを確認する。
2. 修正後に成功することを確認する。
3. 修正前に戻して失敗を確認する場合は、対象ファイルだけを一時退避して実行し、戻したことを `git status` で確認する。

テストがあることと、そのテストが修正を守っていることは別。後者は、修正前に失敗することでしか分からない。

## 実行する検証の選び方

- 変更後は、型・lint・直接影響するunitを必ず流し直す。コマンドの成否は**終了コード**で確認し、出力の一部だけで判断しない。
- browser層の受入条件があるときのE2Eは、`e2e/spec-map.json` の対応と `@smoke` を基準に選ぶ。外す場合は理由を記録する。pathだけを理由にローカル全E2Eを要求しない（`docs/development-process.md` の Functional E2E）。
- repo全体の回帰はCIを正本とし、同じ全件をローカルで理由なく重複しない（`docs/development-process.md` の Verification）。
- UI文言や表示の変更は、その文言を前提にしている既存のunit・E2Eを検索し、期待を更新する。

## コミット前: 差分から対応表を作り直す

`git diff HEAD`（staged・unstagedの両方を含む）の変更を1件ずつ、対応するテストに結びつける（後ろ向き）。

```text
| 変更箇所 | 振る舞い | テスト | 判定 |
```

表のどこにも対応しない変更は、テストを足すか、「振る舞いを変えない」「範囲外」と理由を書く。

## PR本文

- 実行した検証だけを書く。未実行は、理由と正本（CI等）を添える。
- 既存テストの期待やデータを変えた場合は、何を・なぜ変えたかを書く。ガードの意図を変えていないことを示す。
- バグ修正・機能追加で修正前に失敗するテストを置いた場合は、red→greenの結果（修正前に失敗した件数、修正後に成功した件数）を書く。リファクタ・UIのみの変更は、前後で成功のままか、決めた確認方法の結果を書く。
