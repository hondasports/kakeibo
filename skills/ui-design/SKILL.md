# UI/UX設計

Suzumemoの画面やコンポーネントを追加・変更・レビューする前に読む。アプリの振る舞いを変える変更では `skills/implementation`、テスト設計では `skills/test-design`、差分レビューでは `skills/repo-code-review` も併用する。

## 正本

- 製品のUI/UX方針と画面仕様: `docs/ui-ux-design.md`
- ブランド解釈とページ別適用方針: `docs/suzumemo-theme.md`
- 色・余白・角丸・タイポグラフィ: `src/designTokens.ts` と `docs/design-tokens.md`
- MUIテーマへの反映: `src/theme.ts`

汎用的なデザイン論や外部Skillの推奨で、上記の正本を上書きしない。新しい配色、フォント、レイアウト方針を導入する場合は、Product / UX判断として扱い、先に正本の更新要否を確認する。

## 設計・実装の進め方

1. 対象画面の目的、主要操作、入力開始から保存後までの流れを確認する。特に、主要操作が迷わず見つかり、保存後も入力内容や次の行動が分かることを受入条件へ落とす。
2. `src/features/ui`、対象feature、MUIコンポーネントの既存patternを先に探し、再利用する。新しいpatternを作る場合は、既存patternで表現できない理由を残す。
3. 通常・空・読込中・保存中・成功・入力エラー・通信エラー・無効化のうち、対象に必要な状態を列挙する。状態によってレイアウトが大きく崩れたり、入力済み内容が失われたりしないようにする。
4. PCとスマートフォンの両方で確認する。ブレークポイントは既存仕様に合わせ、スマートフォンでは横スクロールを発生させず、主要操作へ到達できる構成にする。
5. 実装後は、対象画面を実際に表示して確認する。表示確認の方法は `skills/test-design` に従って選び、ブラウザ実行が必要な場合は `skills/local-dev-env` に従う。

## 視覚とコンポーネント

- 視覚値は `src/designTokens.ts` をSSoTにする。色・余白・角丸・サイズをコンポーネントへ直接書く前に、既存トークンとMUI themeで表現できないか確認する。
- MUIをUIコンポーネントの主軸にする。見た目はMUI theme、`sx`、`styled` の順で検討し、Tailwind CSSはレイアウト補助に限定する。MUIコンポーネント内部をTailwind CSSで深く上書きしない。
- Suzumemoのブランド色と紙のような背景は意図した設計として維持する。一般的な「AIらしい見た目」を避けるためだけに、正本の配色やフォントを変更しない。
- 装飾的なカード、大きなヒーロー表現、過剰なアニメーションで入力効率を落とさない。動きを使う場合は、状態変化を理解しやすくし、`prefers-reduced-motion` に配慮する。
- 金額と件数は読み取りやすくする。状態やカテゴリを色だけで伝えず、ラベル、アイコン、形状など別の手がかりも併用する。

## アクセシビリティと文言

- キーボードだけで主要操作を完了でき、フォーカス位置が分かるようにする。アイコンのみのボタンにはアクセシブルな名前を付け、開閉UIでは `aria-expanded` など必要な状態を関連付ける。
- フォームエラーは対象項目の近くに表示し、修正方法が分かる文言にする。通信エラーでは再試行方法を示し、入力内容を保持する。
- ボタンやリンクの文言は、対象と結果が分かる具体的な動詞にする。既存画面で使われている文言と表記を優先し、内部用語や実装都合の表現をユーザー向け文言へ出さない。
- スマートフォンの主要なタップ対象は、画面仕様がある場合はそれに従い、指定がない場合は44px程度を目安にする。

## レビュー

UI差分をレビューするときは、次を確認する。

- 主要導線と保存後の状態が `docs/ui-ux-design.md` の画面仕様と一致しているか
- 新しい視覚値が `src/designTokens.ts` とMUI themeを経由しているか
- PC / スマートフォンで情報の欠落、重なり、横スクロールがないか
- 空・読込・保存・成功・エラー状態で操作可否と入力内容の保持が正しいか
- キーボード操作、フォーカス、ラベル、エラー通知が不足していないか
- 文言が既存画面と一貫し、次の行動が分かるか

外部Skill `web-design-guidelines` が利用できる環境では、出荷前の汎用チェックとして併用してよい。ただし、その指摘はこのSkillと正本に照らして取捨選択し、正本と矛盾する一般論を根拠にブランド、MUI方針、画面仕様を変更しない。指摘は対象ファイルと行、根拠になる正本、具体的な修正案をセットで残す。
