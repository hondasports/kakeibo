# テスト設計の判断例

例は判断の出発点であり、全変更への一律な必須ケースではない。新しい導線や境界、故障の影響、既存テストのassertと実行環境で選び直す。

| 変更・目的 | 選び方の例 | 区別する保証 |
| --- | --- | --- |
| 税の丸め | unitで端数や値が変わる境界を独立した期待値で確認する | 既存E2Eが必要な保存・再表示経路を守るなら、計算の全組み合わせをE2Eに増やさない |
| 支出の登録 | componentで入力・エラー、server結合で保存や認可を確認し、必要ならE2Eで登録から一覧等まで確かめる | 成功通知やフォーム消去だけでは保存・再取得を証明しない。表示する値や時点はassertに合わせて記述する |
| グループ境界 | 操作に応じ未認証、別グループ、member／ownerの許可・拒否と副作用をserver側で確認する | UIの出し分けはserver認可の代わりにならない。システム管理者の権限と家計の所属権限も分ける |
| 表示変更 | componentで受入条件に必要な表示を確認する | 実ブラウザのフォーカスや操作を守る必要があればbrowserテストも検討する。DOM上の存在だけでは表示や操作性を保証しない |
| バグ修正 | 修正前に失敗する再現テストを、故障を直接確かめられる適切な層で用意する | 画面で見つかった不具合でも原因が計算ならunitで再現できる。結合固有の故障ならその経路も確認する |

## 外部AIの代役

解析済みの結果を固定して返すmockなら、結果を受け取ってからの確認・修正・登録を検証できるが、実サービスへのリクエスト生成・応答解析や認証は通らない。HTTP応答を代役にする場合は、その応答が実際のAPI契約と食い違う可能性を考慮し、実装の解析処理と実サービス接続のどちらを確認したか分けて記録する。いずれも実際の解析精度や本番設定まで保証しない。

## 既存E2Eとの比較

必須入力エラーをcomponentとE2Eの双方が確認する場合、エラー表示・送信しないこと・ブラウザ描画のどれを各assertが直接確認するか比べる。componentが送信先をmockしていることや、E2Eの実行契機の差も考慮する。別のテストが同じ保証を持つと判断するなら、入力・認証・前提・対象・保存前後の時点・環境などの違いと、無関係とする理由を示す。

一覧の存在確認を行うE2Eが、保存された全件の金額や再読み込み後の値まで確認するとは限らない。assertが直接確認する内容、部分的な確認、対象外を分ける。失う保証がないとする場合も、代替テストとその根拠を示す。実行していないテストについては、故障を実際に検出したとは断定しない。
