# 軽く・サクッと記録できるWeb家計簿 UI/UX設計

## 1. 目的

本ドキュメントは、MVP実装に向けたUI/UX方針を定義する。

本アプリのUIは、見た目の派手さよりも、ユーザーが「記録しよう」と思った時に迷わず入力を始め、1件だけでも複数件でも無理なく記録できることを最優先にする。

## 2. UX/UIコンセプト

コンセプトは「思いついた時に、軽く・サクッと支出や収入を記録できる静かなメモ帳」とする。

- 記録しようと思った時から入力開始まで迷わせない
- 1件だけの入力でも大げさなセッション開始を要求しない
- 保存後、ユーザーは終了しても続けて入力してもよい
- 複数レシートは連続入力またはAI下書きキューでまとめて処理できる
- 手入力とAI入力のどちらかを正解として強制しない
- 週次サマリーは入力義務の完了画面ではなく、記録済みデータの振り返り画面として扱う
- 1枚入力するたびに、件数と合計の変化がすぐ見えるようにする
- 主要操作は `保存して次へ` を中心に置く
- MUIを使うが、標準Material Design感は抑え、静かで軽い独自テーマにする
- Tailwind CSSは画面骨格、余白、レスポンシブなどのレイアウト用途に限定する

## 3. デザイン方針

### 3.1 見た目

- 家計簿向けの落ち着いた生活感を重視する
- 業務ツールに近い、読みやすく操作しやすいUIにする
- 装飾的なカードや大きなヒーロー表現は使わない
- 角丸は8px以下を基本にする
- 余白は広げすぎず、入力作業に必要な情報密度を保つ

### 3.2 カラー

- 主色は深めのグリーンまたはティールを候補にする
- 削除などの危険操作は控えめなレッドを使う
- カテゴリ色は区別しやすさを優先し、強すぎる彩度を避ける

### 3.3 タイポグラフィ

- 画面内の見出しは大きくしすぎない
- 金額と件数は視認性を高める
- フォームラベルと補助文は短くする

## 4. ユーザーフロー

1. Googleアカウントでログインする
2. ダッシュボードで最近・今週の記録状況を確認する
3. 必要なタイミングで支出/収入の入力を開始する
4. 手入力またはAIレシート入力を利用する
5. 1件で終了する、続けて入力する、AI下書きを確認する、のいずれも選べる
6. 必要なタイミングで週次サマリーから支出傾向を振り返る
7. **週別支出推移グラフで対象週と直前2週間を比較し、棒のTooltipで週範囲と支出合計を確認する**

## 5. 画面構成

### 5.1 ダッシュボード `/`

目的は、最近の状況と入力再開導線をすぐ見つけられるようにすることである。

表示する情報:

- 今週の合計支出
- 今週の合計収入
- カテゴリ別支出
- 入力済みレシート件数
- 未完了セッション
- 前週比

主要操作:

- `入力を開始`
- `入力を再開`
- `週次サマリーを見る`

注意:

- ダッシュボードを作り込みすぎない
- MVPでは、入力画面への導線を最も目立たせる

### 5.2 入力画面 `/weeks/current/input`

MVPで最も重要な画面とする。

現行コードでは、週ナビゲーション、`ExpenseEntryForm`（手入力）、`AiExpenseQueuePanel`（AI下書きキュー）を
配置する。1件だけの入力から複数件の連続入力まで、同じフォームで無理なく処理できる。スマートフォンでも入力フォームを最優先にし、保存後すぐ次の入力に進める。

表示する情報:

- 週ナビゲーション
- 手入力フォーム（`ExpenseEntryForm`）
- AI支出下書きキュー（見出し「レシート入力」）

主要操作:

- `保存して次へ`（手入力）
- AI下書きの確認・編集・まとめて登録

### 5.5 公開ページ

| パス | 目的 |
| --- | --- |
| `/privacy` | プライバシーポリシー（認証不要） |
| `/terms` | 利用規約（認証不要） |
| `/maintenance` | メンテナンス表示（認証不要） |

フッターから公開ページへ遷移できる。詳細は `src/features/app-shell/lib/publicPaths.ts` を参照する。

### 5.3 週次サマリー `/weeks/:weekStartDate`

目的は、入力後にその週の支出傾向を把握できるようにすることである。

表示する情報:

- 合計支出
- 合計収入（合計支出の直下）
- カテゴリ別支出
- 前週比
- **週別支出推移（対象週を含む直近3週間の棒グラフ）**
- 支出一覧（レシート単位で店舗名・合計金額を表示し、店舗名の下に項目名・金額・カテゴリの内訳を表示。各明細にメモがある場合は表示。3行以上または折り返しで2行超になる場合は「もっと見る」で展開、「閉じる」で折りたたみ）
- 収入一覧（支出一覧と同様の行形式。カテゴリ列なし。5件超は「さらにN件を見る」で展開）

**支出一覧のメモ表示（Issue #359）:**

- 入力時のメモを各支出行の日付・カテゴリの下に表示する
- 表示が2行以内で収まる場合は全文表示し、トグルボタンは出さない
- 改行で3行以上になる、または表示幅での折り返しにより実質3行以上必要になる場合は、初期表示を2行までに制限し「もっと見る」で全文、「閉じる」で2行表示に戻す
- 改行を含むメモは `pre-wrap` で折り返す

**週別支出推移グラフの仕様:**

- 対象週、1週前、2週前の支出合計をprimary色の棒で比較表示
- 各週の棒はカテゴリ別の積み上げで内訳が分かる（上位5カテゴリ + その他）
- 現在週では `今週`、`先週`、`2週前`、過去週では `M/D週` のラベルを使う
- Y軸は金額に応じて `円`・`万円` で表し、PC・モバイルとも文字が見切れない余白を確保する（モバイルは左余白を抑える）
- グラフ外の独立した3指標パネル（`SummaryMetricsPanel`）に、対象週の支出、前週差、直前2週間の平均比を表示する
- 棒のTooltipに週範囲、支出合計、カテゴリ内訳を表示する
- 各棒の上に週合計、下に週名と週範囲を表示する
- グラフ下にカテゴリ色の凡例を折り返し可能な形で表示し、モバイルでも横スクロールさせない
- モバイルでも約220pxの固定高でラベルを読み取れるようにする
- 空状態: 「週別の支出データがあると表示されます」
- ローディング: Skeleton で表示

主要操作:

- 支出を修正する
- **グラフの棒をホバーまたはタップして週ごとの比較を見る**

**レスポンシブ構成（Issue #371）:**

- ヘッダーの状態Chipは週セッションが存在する場合のみ表示し、セッション未作成の過去週では表示しない
- PCでは、合計支出・前週差・2週平均比を横並びにし、週別支出推移とカテゴリ別内訳を2カラムで表示する
- スマートフォンでは、3指標、週別支出推移、カテゴリ別内訳、支出一覧の順に1カラムで表示する
- カテゴリ別内訳はPCで金額・割合・件数を持つ表、スマートフォンで省スペースな一覧とし、合計行を表示する
- 支出一覧はレシート単位の親行と、項目名・金額・カテゴリを持つ明細行で構成する。レシート単位のカテゴリ列は表示しない
- PCでは日付・店名/内訳・金額・メモ・操作の表、スマートフォンでは親行と明細行を境界線区切りの縦積みで表示する
- 週次サマリーの支出一覧だけ、明細行にチェックボックスを常時表示する（月次・検索は対象外）
- 選択中は「明細N件」単位でカテゴリ変更と削除を表示する。カテゴリ変更はプレビュー後に「変更する」で適用し、削除は件数と取り消し不可を確認してから実行する
- 一括カテゴリ変更と一括削除の成功は、設定画面の管理操作ログ（ownerのみ）に件数とカテゴリ差分として残す。undoは提供しない
- 一度に選べる明細は100件まで。表示中の明細の全選択はPCヘッダーと「表示中の明細をすべて選択」から行う
- 支出一覧は最初の5レシートを表示し、残りがある場合は「さらにN件を見る」で全件を展開する
- スマートフォンの編集・削除操作は44px以上を確保し、画面全体に横スクロールを発生させない

### 5.4 設定 `/settings`

`/settings` は、グループ・カテゴリ・週の設定を同一背景上へまとめた「一枚の設定台帳」とする。
`/categories` は同じ設定画面への互換ルートとして扱う。

- セクション順は `グループ`、`カテゴリ`、`週の設定`、`危険な操作` とする
- 独立カードを積まず、余白・見出し・区切り線で階層を表す
- 現在値を先に表示し、追加・編集フォームは必要なときだけ展開する
- 読込・空・エラーはセクション単位、保存中は対象操作単位で表示する
- 危険な操作はownerのみに表示し、初期状態では折りたたむ
- グループ削除dialogは bounded previewを「N件」「100件以上」「件数は削除処理中に確定します」で表示し、即時利用不能・background処理・取消復元不可を明示する
- 削除開始後はGroupRouteGuard外の`/group/delete/status/:jobId`へ遷移し、requested/running/retry_wait/failed/completedを区別する。進捗率、完了見込み、内部エラーは表示しない
- failedではoriginal requesterだけに再開操作を表示し、completed後はグループ選択またはsetupへ進める
- PCでは設定行を横並び、320〜899pxでは同じDOM順のまま縦積みにする
- 長い名前やメールアドレスは折り返し、横スクロールを発生させない
- 開閉操作はキーボードで実行でき、`aria-expanded`と対象領域を関連付ける

グループ管理（メンバー・招待）のセクション構成と owner/member の表示差分は
`docs/group-admin-ui-layout.md` を正本とする。

主要操作:

- グループ名・メンバー・招待を管理する（詳細は `docs/group-admin-ui-layout.md`）
- カテゴリを追加する
- カテゴリ名を変更する
- カテゴリ色を変更する
- カテゴリを無効化する
- 週の開始曜日を保存する（週の終了曜日は開始日から7日間になるよう自動表示する）

### 5.6 システム管理 `/admin`

通常利用者の設定画面と分離し、active なシステム管理者だけが利用する。画面ヘッダーには
現在の環境を常時表示し、「グループ owner」と「システム管理者」を明確に区別する。

権限確認、読込、空、エラー、付与・剥奪中の状態と確認ダイアログの詳細は
`docs/system-admin-authorization.md` を正本とする。管理画面から家計データは表示しない。

## 6. 支出入力フロー

入力コンテンツの先頭で `支出 / 収入` を切り替える。初期値は支出とし、種別ごとの未保存値を
切替後も保持する。

### 6.0 入力ワークベンチのレイアウト契約（実装正本）

breakpoint は **900px**（`max-width: 899px` が SP）。MUI のキュー内 flex 切替も `md`（900px）に揃える。

支出タブの `.input-workbench` 直下は **4 兄弟ブロック**（DOM 順 = SP 表示順）:

| grid-area | クラス | 内容 |
| --- | --- | --- |
| `queue-header` | `input-workbench-queue-header` | レシート入力見出し・追加/撮影ボタン |
| `queue-active` | `input-workbench-queue-active` | ステータスサマリー・処理中/ready/確認待ち/失敗 |
| `form` | `input-workbench-form` | 手入力フォーム |
| `queue-registered` | `input-workbench-queue-registered` | 登録済み一覧 |

- **SP（899px 以下）:** 1 カラム。上表の順（ヘッダー → アクティブ → フォーム → 登録済み）
- **PC（900px 以上）:** 2 カラム。左にフォーム、右にキュー 3 ブロック（ヘッダー → アクティブ → 登録済み）
- `display: contents` や flex `order` による並べ替えは使わない（`grid-template-areas` で配置）
- 収入タブ（`input-workbench--income`）はフォーム単体の 1 カラムを維持する

入力順は以下を基本にする。

1. 日付（週内の曜日選択）
2. 店舗名 / 支払先
3. 合計金額
4. カテゴリ（単一項目、または複数支出項目モード）
5. メモ（任意）
6. 保存

### 6.1 日付

- 初期値は今日、または直前入力の日付にする
- 週内の日付を素早く選べるUIを用意する
- 保存後は前回値を引き継ぐ

### 6.2 店舗名 / 支払先

- 店舗名または支払先を入力する
- 保存後は店舗名/支払先と金額、メモをクリアする

### 6.3 金額

- 合計金額と複数支出項目の内訳合計を扱う
- 複数支出項目モードでは、内訳合計と合計金額の差額を確認ダイアログで確認する
- 入力値は日本円の整数として扱う
- 表示上は円表記を補助する
- スマートフォンでは数字キーボードを出しやすい入力属性にする
- 0円以下は保存できない

### 6.4 カテゴリ

- 店名からカテゴリ候補を推定する
- 推定できない場合は、直近カテゴリやよく使うカテゴリを表示する
- カテゴリは `Chip` または小さな `Button` でタップしやすくする
- 推定が外れても修正しやすいUIにする
- `カテゴリ別の内訳を追加` で複数カテゴリの内訳入力モードに切り替えられる

### 6.5 メモ

- 任意入力とする
- 複数行入力できる TextField とし、改行を保持する
- 通常の入力リズムを邪魔しないよう、折りたたみまたは小さな欄にする
- 上限文字数を設ける

### 6.6 保存

主ボタンは `保存して次へ` とする。

保存後の挙動:

- 日付を引き継ぐ
- カテゴリを引き継ぐ、または店名から再推定する
- 店舗名/支払先、金額、メモをクリアする
- Snackbar で「支出項目を保存しました」と通知する
- 保存結果をダッシュボードや週次サマリーへ反映する

### 6.7 AI支出下書きキュー

`AiExpenseQueuePanel`（見出し「レシート入力」）は、レシート/払込票画像の解析結果を
下書きとして確認してから `expenseEntries` に一括登録する主導線とする。

- `ready` と `needs_review` の違いを状態として見せる
- 必須項目が不足している下書きは、書類種別、日付、合計金額、店名・内容、カテゴリを編集できるようにする
- 標準ではレシート全体のカテゴリを全商品へ適用し、明細ごとのカテゴリ選択欄は表示しない
- 複数カテゴリに分ける場合だけ、各商品にカテゴリ選択欄を表示して個別に変更できるようにする
- 複数カテゴリのレシートはカテゴリ別登録候補を確認画面に表示し、編集後も確認画面へ戻してから登録を確定する
- 確認フォームの主要フィールドは書類種別、支出日（レシート記載日）、合計金額、店名・内容、レシート全体のカテゴリとする。支払場所・支払先・支払内容は店名・内容へ統合する。
- 明細行ではレシートの印字額を編集欄に表示し、外税確定時は直下に登録額（税込・`normalizedAmountYen`）を常時表示する。税率、按分税、数量×単価は詳細または `ReviewItemTaxDetails` で補足する。
- 金額照合パネル（`ReceiptTotalsPanel`）は一致時に「金額一致」と支払額を表示し、要確認時は「内訳を表示」で4行を展開する。お支払い（レシート合計）、登録合計（税込・明細の `normalizedAmountYen` 合計）、印字合計（外税時は税抜ラベル付き・`printedAmountYen` 合計）、レシート小計（`taxSummaries` の対象額）を表示し、印字額は元の値を保持する。
- 確認結果（`ReviewCheckCards`）の金額確認・税率別集計は、商品と対象額の税込・税抜区分が異なっても、確定済み区分と印字税額による換算で完全一致する場合は一致とする。税率別の比較値は印字対象額の区分にそろえる。換算後の1円差、区分不明、矛盾する内訳はこの規則で確定せず、理由を表示して確認を促す。一致した確認カードは表示しない。
- 商品の税率・価格区分を補正して保存した後も、再表示・再保存で商品設定と印字税額を維持する。全体設定で明示した軸だけを復元し、商品のみの「不明」は明細確認、明示的な全体「不明」は合計のみの登録として扱う。
- 税正規化の警告（税率不明、税込・税抜不明、印字額と税率別対象額の差、税率別集計と明細の不一致）は日本語メッセージで件数集約表示する（`formatTaxWarnings`）。
- 画像を1枚だけ追加した場合は解析完了後に確認フォームを自動表示し、複数枚追加時は確認待ち一覧から開く
- 確認フォームの支出日はレシート記載日を初期表示し、確認後は直接登録せず登録準備OKへ移動する
- 明細ごとにカテゴリを選択でき、値引き明細は負数で編集できるようにする
- 値引き明細は負数で編集し、対象商品を選ぶことで同じカテゴリから減額する
- 値引き対象が不明な場合は確認を必須とし、登録後の履歴にはカテゴリ別正味額のみ表示する
- 支払場所、支払先、支払内容は編集画面へ個別表示せず、店名・内容へ統合する
- まとめて登録しても、通常の `expenseEntries` 保存と同じ認可・バリデーションを通す
- 解析中は「読み取り中」等の状態ラベルを表示する
- 確認対象は金額不一致、カテゴリ不足・競合、その他の順に並べ、初期表示は最大3件にする
- 登録済みは直近3件だけを初期表示し、残件は明示操作で展開する

### 6.8 収入入力

- 日付、金額、収入の内容・メモ、`保存して次へ` だけを表示する
- レシート追加・撮影、店舗、支出カテゴリ、カテゴリ別内訳、AI下書きは表示しない
- 保存成功後は日付を維持し、金額と内容をクリアする。失敗時は入力値を保持する

## 7. UI状態

### 7.1 空状態

- ダッシュボードでは `入力を開始` を主導線にする
- 説明文は短くする
- 未入力でも不安を感じない表示にする

### 7.2 ローディング

- MUI `Skeleton` を使う
- フォーム全体をスピナーで塞がない
- 既に表示済みの入力内容はできるだけ保持する
- Clerk / Convex の初期認証待ちは、Suzumemoロゴと左右の葉を使った3秒ループの全画面アニメーションを表示する
- 全画面アニメーションはSuzumemoのペーパーカラー1色を使った半透明オーバーレイとし、内側に別色の背景・枠・影を設けない
- ロゴは既存のSVGだけを使い、左右の葉が芽吹いたあと、英字と日本語の文字が順に現れ、全体を短く保持してからまとめて消える3秒ループにする
- アニメーション本体は `SuzumemoLoadingLogo`、配置と待機文言は `SuzumemoLoadingState` に分離し、`fullscreen` と `page` の表示方式を共通化する
- 認証、グループ確認、Dashboard、入力、週次サマリーなど画面全体またはページ全体を待つ状態には `SuzumemoLoadingState` を使う
- ボタン内の保存・送信中表示には小さい `CircularProgress`、既存レイアウトを保持する読込状態には `Skeleton` を引き続き使う
- 全画面アニメーションには待機内容の文言と `role="status"` を付け、`prefers-reduced-motion` では静止表示にする

## 8. MUIコンポーネント方針

MUIをUIコンポーネントの主軸にする。Tailwind CSSはMUIの代替ではなく、レイアウト補助として使う。

責務分担:

- MUI theme: 色、Typography、角丸、影、コンポーネント標準スタイル
- MUI `sx`: MUIコンポーネント単位の微調整、状態依存、theme参照が必要なスタイル
- MUI `styled`: 再利用する独自コンポーネントや複雑なスタイル
- Tailwind CSS: 画面全体のflex/grid、gap、padding、responsive、表示/非表示、外側ラッパー

`Button`、`TextField`、`Chip`、`Alert`、`Snackbar`、`Table` などのMUIコンポーネントの色、サイズ、角丸、状態表現はMUI themeを正とする。Tailwind CSSでMUIコンポーネント内部を深く上書きしない。

### 8.1 レイアウト

- `Container`
- `Stack`
- `Grid`
- `Box`

### 8.2 入力

- `TextField`
- `Autocomplete`
- `Select`
- `ToggleButtonGroup`
- `Button`

### 8.3 カテゴリ

### 8.4 進捗と状態表示

- `LinearProgress`
- `Badge`
- `Skeleton`
- `CircularProgress`

- `Alert`

### 8.5 一覧

- スマートフォンでは縦積みのリスト表示にする
- スマートフォンで横スクロール前提の表は使わない

### 8.6 ナビゲーション

- PCではサイドナビまたはトップナビを使う
- スマートフォンでは下部ナビまたは上部の最小ナビを使う
- 入力画面ではナビゲーションを主張させすぎない

## 9. レスポンシブ方針

### 9.1 PC

- 週ナビゲーションと入力フォームを読みやすい幅で配置する
- 入力画面では手入力フォームとAI下書きキューを迷わず見つけられるようにする
- キーボード操作を重視する
- 入力後の確認はダッシュボードまたは週次サマリーへ自然に移動できるようにする

### 9.2 スマートフォン

- 1画面1タスクを基本にする
- `保存して次へ` を画面下部に固定する
- カテゴリはタップしやすいチップとして表示する
- 支出一覧はテーブルではなく縦積みリストにする
- サマリーは入力を妨げない位置に置く

## 10. 実装時の注意

- 入力フォームは再レンダリングでフォーカスが飛ばないようにする
- 保存後の初期値引き継ぎを仕様として固定する
- 金額は表示フォーマットと保存値を分ける
- カテゴリ推定は外れても邪魔にならないUIにする
- Tailwind CSSはレイアウト用途に限定し、MUIコンポーネントの見た目制御はMUI theme、`sx`、`styled` を優先する
- CSVエクスポートやオフライン対応は現行コードでは未実装であり、入力セッションの導線から外す
- ダッシュボードよりも、入力画面を先に作り込む
- E2Eでは、複数件の支出入力、複数支出項目モード、設定保存、週次サマリー確認、AI下書き一括登録を変更内容に応じて検証する
