# 軽く・サクッと記録できるWeb家計簿 要件定義

## 1. 概要

本アプリは、思いついた時・支払いを思い出した時・レシートを見つけた時に、軽く・サクッと支出や収入を記録し、あとから支出傾向を振り返るためのWeb家計簿アプリである。

ブラウザで利用できるWebアプリとして提供し、PCとスマートフォンの両方で主要操作を完了できることを前提とする。銀行口座・クレジットカード連携や高精度OCRを前提にせず、手入力とAIによるレシート入力を使い分け、1件だけの入力から複数レシートのまとめ処理まで、入力頻度を強制せず、週単位の振り返りもできる。

## 2. Product Lead判断

### 2.1 初期ポジショニング

本アプリは、資産管理アプリではなく、続けやすい支出・収入の記録を支援するWebアプリとして設計する。

既存の高機能家計簿アプリと正面から競合しないため、MVPでは以下に集中する。

- 毎日入力しなくてもよい
- 好きなタイミングで1件だけでも、まとめてでも入力できる
- 手入力とAI入力を状況に応じて使い分けられる
- 記録した内容を週単位で振り返り、使いすぎに気づける

### 2.2 MVPで検証する仮説

- ユーザーは、入力しようと思った時に短時間で完了できれば家計記録を続けやすい
- 1件だけの入力と複数件のまとめ入力を同じプロダクトで無理なく行える
- 手入力とAI入力を状況に応じて選べることで入力負担を減らせる
- 記録したデータを週単位で振り返ることで使いすぎや支出傾向に気づける
- Webアプリでも、スマートフォンから短時間で入力できれば日常利用に耐えられる

### 2.3 Webアプリとしての初期決定

| 項目         | 初期決定                                  | 理由                                                                                               |
| ------------ | ----------------------------------------- | -------------------------------------------------------------------------------------------------- |
| 提供形態     | Webアプリ                                 | インストール不要で試しやすく、PCとスマートフォンの両方で使えるため                                 |
| 対象端末     | PC、スマートフォン、タブレット            | まとめて入力する場合はPC、レシートを見ながらの軽い入力はスマートフォンでも起こり得るため               |
| 初期保存方式 | クラウドDB保存                            | 複数端末で同じ家計データを同期するため                                                             |
| 認証         | Clerk + Googleアカウント認証をMVPから利用 | クラウド同期ではユーザーごとのデータ分離が必須であり、Google認証なら初回利用の負担を抑えやすいため |
| 同期方式     | Convexを第一候補                          | Reactから扱いやすく、クエリがリアクティブに同期されるため                                          |
| 週の開始日   | 月曜日                                    | 週次振り返りと相性がよく、日本の生活感覚にも合いやすいため                                         |
| 通貨         | 日本円                                    | 初期ターゲットを日本在住ユーザーに置くため                                                         |
| 金額         | 税込合計のみ                              | 明細入力は負荷が高く、MVPの目的から外れるため                                                      |

## 3. コンセプト

- 思いついた時に、軽く記録できる
- 1件だけでも迷わず入力を終えられる
- レシートが複数ある場合はまとめて処理できる
- 手入力とAI入力を状況に応じて使い分けられる
- 入力習慣や頻度をアプリ側から強制しない
- 記録したデータは週単位などで後から振り返れる
- 完璧な資産管理ではなく、続けやすい支出・収入の記録を支援する

## 4. 想定ユーザー

### 主要ユーザー

- 思いついた時にスマートフォンでサクッと支出や収入を記録したい人
- レシートを財布や机に溜めがちな人
- 毎日家計簿をつける習慣が続かない人
- 銀行口座やクレジットカード連携に抵抗がある人
- スーパー、ドラッグストア、外食、現金支出を週単位で見直したい人

### 初期ターゲット

- 一人暮らし、または夫婦・同棲世帯のうち、まずは自分の支出を把握したいユーザー
- 月次の厳密な会計よりも、使いすぎ確認を重視するユーザー
- 手入力とAI入力を使い分けて、入力負担を減らしたいユーザー

## 5. 解決する課題

- 毎日入力する家計簿は心理的負担が高く、継続しにくい
- 高機能な家計簿アプリは設定や連携が多く、始めるまでが重い
- 入力しようと思った時にすぐ始められないと、記録を忘れてしまう
- レシートが溜まると、何にいくら使ったかを後から把握しづらい
- 月末まで振り返らないと、使いすぎに気づくのが遅い

## 6. MVPの目的

MVPでは、ユーザーが好きなタイミングで軽く支出や収入を記録し、その週の支出傾向を確認できる状態を目指す。

成功条件は、ユーザーが次の操作を迷わず完了できることである。

1. 支出または収入を迷わず入力開始できる
2. 1件の入力を短時間で完了できる
3. 複数レシートがある場合は連続入力またはAI入力で処理できる
4. 記録した内容を週単位で振り返れる
5. 必要に応じて設定を確認する

## 7. MVPスコープ

### 作る機能

- 入力セッション（週をまたがない1件入力から、まとめての連続入力まで）
- 支出の手入力（`expenseEntries` を正本。複数支出項目モード、合計金額と内訳の差額確認を含む）
- 収入の手入力（`expenseEntries.entryType: "income"` を正本とし、収入カテゴリは作らない）
- 店名・カテゴリの入力補助
- カテゴリ別集計
- レシート入力済みの進捗表示
- 基本的なカテゴリ管理
- 週の開始曜日のユーザー設定保存（終了曜日は自動算出）
- ClerkによるGoogleアカウント認証
- 複数端末でのデータ同期
- 家族・グループ共有（複数グループ所属、オーナー/メンバー権限、Clerk経由のメール招待）
- 公開ページ（`/privacy`、`/terms`）とメンテナンスモード
- レシート画像から店名・日付・合計金額の候補を抽出する補助PoC
- AI支出下書きキュー（レシート/コンビニ払込票、確認が必要な下書き、まとめて登録）
- システム管理者画面（`/admin`）：ユーザー・グループ検索、監査ログ、権限管理、グループ復旧・削除失敗復旧
- セルフサービス退会（`/settings/account/delete`）：Clerk アカウント削除とグループ脱退の非同期処理

### 作らない機能

- 銀行口座連携
- クレジットカード連携
- 高精度OCRを前提にした自動登録
- レシート明細行の自動確定登録
- サブスク管理
- 資産管理
- 投資管理
- 複雑な予算ルール
- スマートフォンネイティブアプリ
- デスクトップネイティブアプリ
- オフラインファーストの高度な同期
- CSVエクスポートUI（現行コードでは未実装。将来のバックアップ導線として扱う）

## 8. 主要画面

### 8.1 ダッシュボード

目的: 今週の支出状況と入力状況をすぐ確認する。

表示項目:

- 今週の合計支出
- 今週の合計収入
- カテゴリ別支出
- 今週の入力済み件数（`expenseEntries` ベース）
- 前週比

セッション状態（未開始 / 入力中 / 完了）は独立表示せず、主要操作ボタンの文言（「入力を開始」「入力を再開」「週次サマリーを見る」）に内包する。

主要操作:

- 支出または収入の入力を開始する
- 入力中のセッションを再開する
- 週次サマリーを見る

### 8.2 入力画面

目的: 必要なタイミングで、1件だけの支出・収入入力から複数枚のレシート連続入力までを行う。

入力項目:

- 日付（週内の曜日選択 UI）
- 店舗名 / 支払先
- 合計金額
- カテゴリ（単一項目モード、または複数支出項目モード）
- メモ（任意）

入力補助:

- 過去に入力した店名候補
- 店名に紐づくカテゴリ候補
- 直近で使ったカテゴリ候補
- 「カテゴリ別の内訳を追加」から開く複数支出項目モード（内訳合計と合計金額の差額確認ダイアログ）
- 入力後に続けて次のレシートを追加する導線
- AI支出下書きキュー（`AiExpenseQueuePanel`、見出し「レシート入力」）による一括登録
- AI支出下書きキューでは、同一セッション中に追加した画像のサムネイル・拡大プレビューと、解析失敗時の再解析・再撮影を提供する。画像本体は永続化しない。
- 画像を同時に複数選択または撮影した1回の追加操作を1つのセッション限定バッチとして扱い、解析待ち・解析中・確認待ち・失敗・登録準備OKの件数を表示する。
- 「まとめて登録」は同一バッチ内の全画像が`ready`（登録準備OK）になった場合だけ有効にし、`needs_review`や`failed`が残る場合は個別確認・再試行を完了するまで無効にする。別バッチや既存のバッチ情報なしの下書きは登録対象に混在させない。

### 8.3 週次サマリー画面

目的: その週の支出を確認し、次週に活かす。

表示項目:

- 合計支出
- 合計収入（合計支出の直下）
- カテゴリ別支出
- 前週比
- **週別支出推移（対象週を含む直近3週間の棒グラフ）**
- 支出一覧（レシート単位で店舗名・合計金額を表示し、レシート内の項目名・金額・カテゴリを内訳として表示。各明細のメモがある場合は表示。長文は「もっと見る」で展開）
- 収入一覧（支出一覧と同様の行形式。カテゴリ列なし。5件超は展開）

主要操作:

- 支出を修正する
- 支出一覧の明細を複数選択し、カテゴリを一括変更する（ステージ付きプレビューのあと「変更する」で適用）
- 選択した明細を確認ダイアログ付きで一括削除する（取り消し不可、グループメンバーなら実行可）
- 一括削除にundoは無い。カテゴリ変更・一括削除の成功は同一mutationでグループ管理監査ログへ記録する（金額・店名・メモは残さない）。適用前ならキャンセルで破棄でき、適用後の部分失敗は起きない（1件でも不正なら変更ゼロ）
- グラフの棒をホバーまたはタップして週ごとの比較を見る

### 8.4 設定画面

目的: ユーザーが自分の生活に合わせてカテゴリと週設定を管理する。

初期カテゴリ:

- 食費
- 日用品
- 外食
- 交通
- 医療
- 娯楽
- 衣服
- その他

主要操作:

- カテゴリを追加する
- カテゴリ名を変更する
- カテゴリを無効化する
- 週の開始曜日を保存する（終了曜日は自動表示）
- グループを作成する
- 複数所属時に表示対象グループを切り替える
- オーナーがメンバーを招待・削除する

現行実装では `/settings` にグループ管理、カテゴリ設定、週の設定をまとめて表示する。`/categories` は同じ設定画面への互換ルートとして扱う。

### 8.5 エクスポート画面

目的: 入力データを外部で利用できるようにする。

現行コードでは `/export` 画面とCSV生成処理は未実装である。将来のバックアップ導線として要件を残す。

出力形式:

- CSV

出力項目:

- 日付
- 店名
- 金額
- カテゴリ
- メモ
- 週開始日
- 週終了日

## 9. Webアプリ要件

### 9.1 対応環境

- モダンブラウザで動作すること
- PC幅、タブレット幅、スマートフォン幅で主要操作を完了できること
- 初期MVPではネイティブアプリ化を行わない
- PWA対応は将来拡張とする

### 9.2 レスポンシブ方針

- PCでは、週ナビゲーションと入力フォームを読みやすい幅で配置する
- スマートフォンでは、1画面1タスクを基本にして、連続入力を妨げない
- 主要ボタンはタップ操作しやすいサイズにする
- 表形式の情報はスマートフォンで横スクロール前提にせず、カードまたは縦積み表示に切り替える

### 9.3 保存とデータ保護

- MVPではクラウドDBに家計データを保存する
- グループごとのデータ分離を必須とする
- 認証していないユーザーは家計データを作成、閲覧、更新、削除できない
- CSVエクスポートは現行コードでは未実装であり、将来ユーザーが自分でバックアップできる手段として検討する
- オフライン入力はMVPでは必須にしない

### 9.4 入力体験

- 1件だけの入力でも、大げさなセッション開始を要求しないフォームにする
- レシートを見ながら片手でも入力しやすいフォームにする
- 保存後は次の入力にすぐ進める、終了する、AI下書きを確認する、のいずれも選べる
- 日付やカテゴリは直前入力の値を活用し、同じ操作の繰り返しを減らす
- キーボード操作でも連続入力しやすいこと

### 10.5 Group / GroupMember

家計データの共有単位はグループである。ユーザーは複数グループに所属でき、ログイン後に表示対象のグループを選択または切り替えられる。

| 項目          | 型       | 必須 | 説明                                      |
| ------------- | -------- | ---: | ----------------------------------------- |
| groupId       | string   |  yes | 家計データの所有境界となるグループID      |
| name          | string   |  yes | グループ名                                |
| role          | string   |  yes | `owner` / `member`                        |
| activeGroupId | string   |   no | ユーザーが現在表示対象にしているグループID |

オーナーはClerk invitationを経由して招待メールを送信し、招待を受け入れたユーザーは対象グループの `groupMembers` に追加される。メンバー削除は `groupMembers` からの削除であり、Clerkアカウントや `users` レコードは削除しない。

### 10.6 AI支出下書き

画像解析結果は `receipts` に直接保存せず、`aiExpenseDrafts` と `aiExpenseDraftItems` に下書きとして保存する。

- `aiExpenseDrafts`: 書類種別、解析状態、画像ファイル名（`imageFileName`）、支払先/支払場所/支払内容、候補日付、金額、税率別集計（`taxSummaries`）、税記号・マーカー定義（`markerDefinitions`）、カテゴリ、信頼度、警告、確認理由を持つ。`registeredReceiptId` はレガシー互換用で、主導線では未使用。
- `aiExpenseDraftItems`: 親下書きに紐づく明細行を別テーブルで持つ。印字額、税込・税抜（`amountBasis`）、税率、税マーカー（`markers`/`taxMarker`）、按分税、正規化登録額（`normalizedAmountYen`）、税解決状態（`taxResolutionStatus`/`taxResolutionSource`/`taxReviewReasons`）を保持する。
- 対応する書類種別は `receipt`、`convenience_payment`、`unknown`。
- 状態は `queued`、`analyzing`、`ready`、`needs_review`、`failed`、`registered`。
- 登録時は ready 下書きを `expenseEntries` に変換し（`registerReadyDraftsAsExpenseEntries`）、下書きを `registered` に更新する。
- 商品明細はレシートに印字された行金額（`printedAmountYen`）を保持し、登録は正規化した税込額（`normalizedAmountYen`）とする。税額集計行は明細として登録しない。
- 商品価格と税率別対象額の税込・税抜区分が異なっても、区分が確定し、印字税額による換算後の金額が完全一致する場合は照合・税額配分を行う。価格区分の違いだけを理由に印字税額を税率から再計算せず、商品補正・保存・再表示・登録で印字証拠と計算結果を維持する。
- 外税・内税・税率不明は正規化処理で登録額を算出し、確認不能な場合は警告として下書き確認画面に表示する。
- 手入力 MVP の「税込合計のみ」方針（§2.3）とは別に、AI 解析では明細レベルで税情報を扱う。
- 画像解析時は現在有効なカテゴリ名をOpenAIへ候補として渡し、下書き全体と各商品明細のカテゴリ名を候補内から返させる。
- 画像解析で作成した下書きは単一・複数カテゴリを問わず確認必須とし、確認後に登録準備OKへ移動する。
- 確認待ちまたは解析失敗のカードでは、同一セッション中の画像を使う「再解析」と、新しい画像をカメラまたはファイルから選ぶ「再撮影」を利用できる。画像がセッションにない確認待ちカードも、画像を選び直して既存ジョブを再解析できる。画像本体は永続化しない。
- 解析失敗時の撮影改善ヒントは固定の一般案内とし、画像の暗さ・傾き・ぼけを自動診断した結果とは扱わない。
- 同一バッチの進捗・ジョブID・ファイル名の紐付けはブラウザのReact stateに限り、ページ更新・別セッション・別端末では復元しない。Convex Storage、画像履歴、画像の永続化は行わない。
- 支出日は画像の読込日・登録日ではなく、レシートまたは払込票に記載された日付を初期値としてユーザーが確定する。
- 値引き明細は下書き内で負数として保持し、対象カテゴリの正額明細と合算した正味額を正の `expenseEntries` として登録する。
- 通常はレシート全体のカテゴリを全商品へ適用し、複数カテゴリの場合は明細ごとにカテゴリ変更を可能にする。
- 2カテゴリ以上に分類されたレシートは自動登録せず確認を必須とし、カテゴリ別登録候補の確認後に登録する。
- 値引き対象が不明な場合は対象商品を選択して同じカテゴリから減額する。明細合計と支払合計が不一致の場合と同様に自動按分せず確認を必須にする。

### 10.7 M18. 入力元と支出項目の分離方針

M18では、既存MVP利用者を対象に、レシート、払込票、手入力、AI下書きなどの「入力元」と、カテゴリ別に集計・振り返りする「支出項目」を分離して扱う。

当面の正本は次のように整理する。

- `sourceDocuments`
  - schema 上の正本名とする
  - 何を、どの経路で、どの時点で入力したかを表す
  - レシート、払込票、手入力、AI下書きなどの入力元を保持する
- `inputSources`
  - 説明文やUIで使う言い換えとして扱う
  - 意味は `sourceDocuments` と同じ
- `expenseEntries`
  - カテゴリ別支出項目を表す
  - 「何に、いくら、どのカテゴリとして記録したか」を表す
  - 1つの入力元から複数の支出項目を作れる前提を持つ

schema（`sourceDocuments`、`expenseEntries`、`receiptAnalysisBatches`、`receiptAnalysisImageJobs`）は実装済みである。

現行の移行状況:

1. schema と用語の確定 — **完了**
2. 既存 `receipts` との互換・移行方針の確定 — **完了**（`lib/convex/receipts/spendingEntries.ts`）
3. 週次集計とサマリーの `expenseEntries` 寄せ — **完了**（`lib/convex/receipts/spendingEntries.ts`）
4. 入力元から複数の支出項目を作る UI — **完了**（`ExpenseEntryForm` の複数支出項目モード）
5. AI下書きから支出項目候補を作る導線の整理 — **完了**（`registerReadyDraftsAsExpenseEntries`）

`receipts` は互換層として残し、手入力・AI 登録の正本は `expenseEntries` である。

### 10.8 SystemAdmin

システム管理者権限は `groupMembers.role` と分離し、Convex の `systemAdmins` を正本とする設計である。
MVP は active な `admin` のみを扱い、家計データへの横断アクセス権は付与しない。

**現行コードでは `systemAdmins` テーブル、関連 API、`/admin` UI は実装済み**である。
ユーザー・グループ検索、詳細表示、監査ログ閲覧、権限付与・剥奪、ownerless グループ復旧、
招待取消、グループ削除失敗復旧などが `/admin` から行える。設計の正本は
`docs/system-admin-authorization.md` を参照する。

## 11. ユーザーストーリー

- ユーザーとして、支出や収入を思いついた時に軽く記録したい。そうすることで、財布にレシートを溜めずに済む。
- ユーザーとして、店名と金額だけで素早く支出を登録したい。そうすることで、入力の負担を減らせる。
- ユーザーとして、前回使った店名やカテゴリを候補表示してほしい。そうすることで、同じ入力を繰り返さずに済む。
- ユーザーとして、1 枚のレシートから複数カテゴリの支出項目を入力したい。そうすることで、内訳を正確に記録できる。
- ユーザーとして、カテゴリ別に今週の支出を見たい。そうすることで、何に使いすぎたかを把握できる。
- ユーザーとして、レシート画像から候補を作りたい。そうすることで、手入力の負担を減らせる。
- ユーザーとして、AI下書きを確認してまとめて登録したい。そうすることで、入力作業を短くできる。
- ユーザーとして、グループのメンバー状態やロール、オーナー権限、グループ削除に変更があった場合にメール通知を受け取りたい。そうすることで、自分のグループ状態の変化をすぐに把握できる。
- ユーザーとして、AIレシート解析で確認が必要なものが残った場合、60分後にメールで知らせてほしい。そうすることで、確認漏れを防げる。
- ユーザーとして、入力データをCSVで出力したい。そうすることで、表計算ソフトなどで再利用できる（現行UIでは未実装）。

## 12. 受け入れ条件

### 12.1 入力セッション

- ユーザーは現在週の入力セッションを作成できる
- 既に現在週のセッションがある場合は、そのセッションを再開できる
- セッションには週開始日と週終了日が設定される

### 12.2 支出入力

- ユーザーは日付、店舗名/支払先、金額、カテゴリを入力して支出を `expenseEntries` に保存できる
- 複数支出項目モードでは、内訳合計と合計金額の差額を確認してから保存できる
- 保存成功時に「支出項目を保存しました」と表示される
- 入力画面で支出と収入を切り替え、収入は日付・金額・内容で保存できる
- 収入ではレシート操作、店舗、支出カテゴリ、カテゴリ別内訳を表示しない
- 金額が0以下の場合は保存できない
- 必須項目が未入力の場合は保存できない
- 保存後、続けて次のレシートを入力できる

### 12.3 集計

- ダッシュボードに今週の合計支出が表示される
- ダッシュボードに今週の合計収入が表示される（Issue #395）
- カテゴリ別の合計金額が表示される
- **週次サマリー画面に対象週を含む直近3週間の支出合計が棒グラフで表示される**
- **棒グラフの金額軸が円・万円の理解しやすい表記で、画面幅にかかわらず見切れず表示される**
- **グラフ上部に対象週の支出、前週差、直前2週間の平均比が表示される**
- **同じ指標パネル内の合計支出の下に、対象週の合計収入が表示される（Issue #378）**
- **収入一覧に入力済みの収入が表示される（Issue #378）**
- **支出一覧はレシート単位でまとめ、レシート単位のカテゴリ列は表示せず、各明細のカテゴリを表示する**
- **棒のTooltipで週範囲と支出合計を確認できる**
- **直前2週間の支出がともに0円の場合、平均比は比較データなしと表示される**
- 予算金額や予算残額は表示しない

### 12.4 振り返り

現行UIでは振り返りメモと週次セッション完了操作を表示しない。既存データとの互換性を保つため、
保存済みの `reviewMemo` とセッション状態は削除しない。

### 12.5 CSVエクスポート

現行コードでは未実装。将来実装時の受け入れ条件は次のとおり。

- ユーザーは指定した週の支出をCSVで出力できる
- CSVには日付、店名、金額、カテゴリ、メモ、週開始日、週終了日が含まれる

### 12.6 グループ削除

- active group の owner だけが、bounded な影響範囲と対象名を確認して削除を開始できる
- 削除要求の受付と同時に対象グループを利用不能にし、依頼者の `activeGroupId` を解除する
- 完全削除は取消・復元できない background job とし、依頼者は専用画面で開始・処理中・自動再試行・失敗・完了を確認できる
- 失敗時の再開は開始時に記録した original requester だけが同じ job に対して実行できる
- 旧メンバーへ開始・完了を、terminal failure 時は依頼者へ失敗を、再実行で重複しない形で通知する
- `users`、Clerk アカウント、ほかのグループは削除しない

- 将来的な画像解析、AI登録、複数グループ運用に備え、MVPでは依存しすぎない構造にする

## 17. レシート画像入力PoC方針

M11「レシート画像入力PoC」では、手入力を主導線にしたまま、画像から店名・日付・合計金額の候補を抽出する補助機能を扱う。

### 17.1 外部API送信

- 初回実装では、Convex Action から OpenAI Vision 対応 API へ画像を送信する方式を許容する。
- ユーザーが初めて画像読み取りを実行する前に、外部API送信への同意ダイアログを表示する。
- 同意がない状態では、画像データを外部APIへ送信しない。
- 同意済み状態はユーザー単位で Convex に保存し、次回以降の読み取り判定に使う。

### 17.2 画像保存と保持期間

- 初回PoCでは、レシート画像を長期保存しない。
- 画像はブラウザ上の一時プレビューと、解析リクエスト用の一時データとしてのみ扱う。
- Convex Storage に画像を保存しない。
- 監査や改善用の永続ログを追加する場合も、画像そのものは保存対象にしない。

### 17.3 ユーザー向け説明文

画像読み取り導線では、次の内容を短く説明する。

- 読み取り時はレシート画像を外部APIへ送信する。
- 画像は長期保存しない。
- 読み取った店名・日付・金額は候補としてフォームに反映される。
- 抽出結果は自動保存されず、ユーザーが確認・修正してから通常の保存操作を行う。
- 同意しない場合や読み取りに失敗した場合も、手入力を継続できる。

### 17.4 保存フロー

- 抽出結果は receipt として自動保存しない。
- 既存の `保存して次へ` を押したときだけ、通常のレシート保存処理を行う。
- 失敗時、低信頼度、読み取り不能、または同意拒否時は、同じ入力フォームで手入力へ戻れることを必須とする。

## 19. N2. P1 LINE連携基盤（後続拡張）

LINE連携は、既存のWeb家計簿MVPやClerkによる認証を置き換えず、認証済みユーザー本人が別チャネルから家計データを読み取り専用で確認するための後続拡張として扱う。

### 19.1 初期MVPの境界

- 初期のLINE参照MVPは、本人の読み取り専用サマリー参照に限定する。
- LINEからの支出・収入の登録、更新、削除、画像取得、AI解析、汎用チャットは含めない。
- LINEを利用しないWebユーザーの既存導線を変更・置換しない。
- LINE参照サマリーの期間は、連携ユーザーの`weeklyStartDay`（未設定時は月曜始まり）と`Asia/Tokyo`の今日から決める「今週」を正とする。
- 表示対象グループはWebと同じ`activeGroupId`解決を使う。未所属はグループ作成案内、複数所属で未選択はWebでのグループ選択案内を返し、家計金額は出さない。
- テキストコマンドで、今週の支出合計、今週の収入合計、カテゴリ別支出、直近3週間の支出推移、およびグループ内カテゴリ名（例: 食費）の個別参照を返す。未知のテキストは使い方案内のみ返す。
- Messaging API channel には、既存テキストコマンドを送る default Rich Menu を置ける。タップは手入力と同じ message action とし、グループ固有のカテゴリ名や画像・登録操作はセルに置かない。設置は人間が非Production channelで行う。

### 19.2 基盤の依存順

次の順序で実施する。

1. #591: LINE連携のMVP境界、環境分離、運用・検証方針
2. #592: LINE Login OAuth 2.1 + PKCEによるアカウント連携・解除
3. #593: Messaging API Webhook受信、署名検証、イベント冪等処理
4. #185 / #186 / #187: サマリー参照、画像受信、画像AI下書き化

各環境ではLINE Login channelとMessaging API channelを同一LINE Provider配下に置く。Development、Preview、Productionの環境間ではProvider、channel、callback URL、Webhook URL、secretを混在させない。

### 19.3 N5 画像受信とAI下書き

N2の初期読み取り専用MVPに加え、後続のN5では連携済みユーザーが1:1で送ったレシート画像をintakeできる。

- 画像本体は長期保存せず、Messaging APIから一時取得して解析する。Convex Storage へ保存しない。
- OpenAI送信前に、既存Webの `receiptImageExternalApiConsentAcceptedAt` を要求する。LINE画像送信を同意とは扱わない。
- 作成した下書きは Web の画像作成と同じく確認必須（`needs_review`）とし、LINE側での登録・編集・削除は行わない。
- 未連携ユーザーの画像は取得・解析・保存しない。

### 19.4 N5 P4 操作選択と自然文

N5では、読み取り専用サマリーの操作をタップと自然文の両方で選べるようにする。

- Messaging API channel の default Rich Menu は、読み取り専用サマリーの6セル（message action）を維持する。セルにグループ固有のカテゴリ名や、画像送信・登録操作は置かない。
- 「レシートを送る」と「Webアプリを開く」は、ヘルプ文面とサマリー返信のクイックリプライで出す。レシート案内は画像送信を促すだけで、LINE上の登録・編集・削除は行わない。
- Web導線は `APP_BASE_URL` の `/weeks/current/input` を使う。
- 未連携ユーザーには家計操作のクイックリプライを付けず、連携案内を優先する。channel defaultメニューは全ユーザーに見えるが、返信は連携案内のみとする。
- テキストコマンドは完全一致に加え、代表的な言い回しをルールベースで解釈する。解釈できない入力はカテゴリ検索へ落とさず使い方へ誘導する。
- 汎用チャットボット化やLLMによる意図判定は行わない。
