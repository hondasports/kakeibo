# Codex GitHub PR レビューの評価・運用基準

この文書は `kakeibo`（Suzumemo）の PR レビューを評価するための日本語の運用資料。**実際に Codex へ適用するルールの正本はルートの `AGENTS.md` の「Code Review Rules」** とする。この文書だけを更新しても Codex のルールは更新されない。

## 目的と適用範囲

- 重大な不具合に加え、実害につながる設計上の欠陥を発見する。
- 理想的な設計パターンの押し付けや、CI で判定できる軽微な指摘を避ける。
- Codex は追加のレビュー担当。CI・ブランチ保護・必要な人間の承認を代替しない。
- `skills/repo-code-review/SKILL.md` は実装エージェントによるセルフレビューの手順であり、GitHub 標準の Codex レビューとは別。独立 Reviewer の要否は `docs/development-process.md` を優先する。

## 指摘コメントの言語

- Codex が GitHub PR に投稿するレビューコメントは日本語で記述する。インラインコメント、レビュー全体の要約、指摘タイトル、問題の根拠・再現条件・影響・修正案・確認事項まで適用する。
- 識別子、ファイルパス、コマンド、ログ、コード、`P0` / `P1` などの重大度ラベルは原文を維持してよい。説明文のみ日本語とし、技術的な正確性を優先する。
- レビュー結果の検証時には、重大な違反を検出したかだけでなく、**指摘の自然言語が日本語になっているか**も確認する。

指摘例（実際のレビューで発見された問題ではなく出力形式の例）:

```text
[P1] グループ所属を検証せず家計データを返している
根拠: 指定した groupId の所属確認がないため、他グループの家計データを閲覧できます。
発生条件: 未所属の groupId を指定してこの query を呼び出した場合。
影響: 他グループの家計情報が漏洩します。
修正案: Convex 側で認証済みユーザーの groupMembers 所属を確認してください。
```

## 評価領域

| 領域 | 指摘する条件の例 | 原則指摘しない例 |
| --- | --- | --- |
| 正確性・回帰 | 通常の操作や境界条件で既存機能が破綻する | 結果が同じ実装方法の違い |
| セキュリティ | 未所属グループの家計データを取得できる、secret が漏れる | 再現条件も根拠もない漠然とした懸念 |
| データ整合性 | 再試行による二重登録や、部分失敗によるデータ不整合 | トランザクションを使っていないという事実のみ |
| 設計品質 | 責務・信頼境界を破壊し、認可漏れや整合性破綻につながる | 関数分割・命名・抽象化の好み |
| 互換性 | 既存データや外部連携が移行なしに利用不能になる | 後方互換を維持した内部変更 |
| テスト品質 | 重大な不変条件の回帰リスクが具体的に未検証となる | カバレッジの数値のみ |
| パフォーマンス | 増加するデータ量に対し、主要導線に著しい悪影響を与える | 根拠のない微小な最適化要求 |

設計品質では **責務・依存方向／信頼境界／状態と副作用／変更影響範囲** を確認する。ただし「パターンが好みでない」こと自体は指摘理由にならない。

## 重大度の運用目安

| 重大度 | 判断の目安 | 扱い |
| --- | --- | --- |
| P0 | 広範囲のデータ破壊や直ちに対応すべき致命的リスク | 緊急対応 |
| P1 | 通常条件で主要機能・機密性・整合性を重大に損なう | マージ前に修正 |
| P2 | 限定条件の不具合、具体的な中程度の設計リスク | 人間の追加レビュー等で扱う |
| P3 | 軽微な保守性・可読性改善 | 原則レビューコメント不要 |

これはリポジトリの運用上の目安。GitHub 標準の Codex コードレビューは重大な P0/P1 に重点を置くため、P2/P3 を報告させる目的で重大度を引き上げない。すべての指摘が GitHub へ必ず投稿されるわけではない。

## 指摘の品質

レビュー結果を採用する前に、次を確認する。

1. **差分との因果関係:** 今回の変更が導入・悪化させた問題か。
2. **発生条件:** 再現可能な入力・操作・タイミング・対象ユーザーなどを説明できるか。
3. **影響:** 誰に、どのデータや機能に、どの程度の実害があるか。
4. **修正の方向:** 問題の解消方法が具体的で、既存仕様と矛盾しないか。

セキュリティの深刻な疑義で再現手順が未確定な場合は、結論を断定せず証拠不足を明示して人間の確認へ回す。レビュールールの違反と判定する前に、正常な例外や既存の防御層を確認する。

## リポジトリ固有の正本

- グループ所属・共同利用: `docs/group-admin-permissions.md`
- 認証・グループガード: `docs/auth-guard.md`
- システム管理者の権限・監査: `docs/system-admin-authorization.md`
- コードの専門的なセルフレビュー: `skills/repo-code-review/SKILL.md`
- セキュリティ境界: `skills/security-review/SKILL.md`
- ブランチ運用・独立レビューの条件: `docs/development-process.md`

仕様の変更が確認された場合は上記の正本を先に更新し、`AGENTS.md` を追随させる。古いルールによる誤検知が出た場合は根拠を確認して修正・削除する。

## 代表的な評価ケース

| ケース | 差分に含める変更 | 期待する結果 |
| --- | --- | --- |
| 違反: グループ境界 | 未所属 `groupId` を指定して家計データを読めるようにする | 差分位置と実害を示した重大な指摘 |
| 正常: グループ共同利用 | サーバー側で所属を検証して同じグループのメンバーに閲覧を許可する | 「他ユーザーのデータ」という理由で誤検知しない |
| 違反: 管理者境界 | `requireSystemAdmin` だけで家計を読めるようにする | 管理権限と家計アクセスの混同を指摘 |
| 違反: 削除・監査 | グループ削除時に監査仕様で必要な記録まで失う | 契約と影響を示した指摘 |
| 正常: 削除・監査 | 仕様で定められた対象のみ削除し、必要な監査記録を保持する | 誤検知しない |
| 違反: 集計 | JST の月境界を UTC に変更し月末の家計が別月になる | 実際の境界条件を伴う指摘 |
| 無関係 | 文言・スタイルだけ変更する | 認可や税計算の無関係な指摘をしない |
| 一般バグ | 固有ルールと無関係な明らかな回帰を混ぜる | 固有ルール以外の通常のバグ検出も維持する |

各評価ケースでは、指摘がある場合にコメントのタイトル・本文が日本語になっていることも確認する。識別子やコード片は原文で構わない。

検証時は小さな検証用 PR を使い、問題のある変更を `preview` にマージしない。**この文書の追加だけでは評価ケースを実行済みとはみなさない。**

## 共通ルールの配布・変更管理

1. ルート `AGENTS.md` の `BEGIN SHARED CODE REVIEW RULES` と `END SHARED CODE REVIEW RULES` の間を、共通ルールの配布領域とする。
2. 現段階では **このリポジトリの内容だけを確定**する。専用の共通ルール管理リポジトリ、自動同期スクリプト、同期用 GitHub Actions はまだ作成していない。
3. 今後、複数リポジトリへ展開する際は共通ルールの管理リポジトリを正本として作り、各リポジトリのこの領域だけを更新する PR を生成する。固有ルールと他のエージェント契約には触れない。
4. 共通ルールを変更する場合、違反・安全・無関係の評価ケースを確認してから配布する。管理する版番号は配布スナップショットに残す。

## 導入後の確認

- GitHub の Codex Code Review を対象リポジトリで利用できるかは別途確認する。
- 代表的な次の PR で `@codex review` を実行し、指摘の妥当性と不要なコメントの有無を確認する。
- レビュー投稿が無いことだけを理由に、規則が機能していない／バグが存在しないと断定しない。
- CI は PR の最新 HEAD を対象に確認する。ルールの変更だけで実装テストが実行されたことにはしない。
